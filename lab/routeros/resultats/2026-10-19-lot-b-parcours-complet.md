### Constats

- Le code du ticket est le nom d'utilisateur : il apparaît **en clair sur le routeur** (`/ip/hotspot/active`, nom de la file dynamique `<hotspot-…>`, `/log` rubrique hotspot). Inhérent aux tickets à code unique ; à garder en tête pour qui a un accès en lecture au routeur.
- `Mikrotik-Total-Limit` et `Mikrotik-Rate-Limit` sont tous deux appliqués par RouterOS 7.24.5 en Hotspot.
- Aucune correction de la configuration FreeRADIUS ni de l'API n'a été nécessaire. Corrections apportées au laboratoire et à la documentation : règle UDP 1812/1813 du firewall de passerelle ; section « Rôle ecsi_radius » de `docs/DEPLOYMENT.md` (le message d'erreur de la migration 0008 y renvoie).

### Étape 1 : rôle puis migrations (laboratoire)

```sh
S=lab/sim/.state/s3b; source "$S/env"
export DATABASE_MIGRATOR_URL="postgres://ecsi_migrator:$PGM@127.0.0.1:15432/ecsi"
node apps/api/dist/database/migrate.js          # refus attendu sans le rôle
( umask 077; grep -q '^PGR_VPS=' "$S/env" || echo "PGR_VPS=devonly-radius-$(openssl rand -hex 20)" >>"$S/env" )
source "$S/env"; export ECSI_DB_RADIUS_PASSWORD="$PGR_VPS"
docker exec -i -e ECSI_DB_RADIUS_PASSWORD ecsi-s3b-pg psql -v ON_ERROR_STOP=1 -U postgres -d ecsi <<'SQL'
SET log_statement = 'none';
SET log_min_error_statement = 'panic';
SET log_min_duration_statement = -1;
\getenv radius_password ECSI_DB_RADIUS_PASSWORD
CREATE ROLE ecsi_radius LOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB NOBYPASSRLS PASSWORD :'radius_password';
GRANT CONNECT ON DATABASE ecsi TO ecsi_radius;
SQL
unset ECSI_DB_RADIUS_PASSWORD
node apps/api/dist/database/migrate.js          # 0008 + 0009
docker exec ecsi-s3b-pg psql -U postgres -d ecsi -At \
  -c "select count(*) from drizzle.__drizzle_migrations" \
  -c "select rolname, rolsuper, rolbypassrls, rolcanlogin from pg_roles where rolname = 'ecsi_radius'" \
  -c "select count(*) from information_schema.role_table_grants where grantee = 'ecsi_radius'" \
  -c "select count(*) from information_schema.role_routine_grants where grantee = 'ecsi_radius' and routine_schema = 'radius'"
```

### Étape 2 : FreeRADIUS dans le namespace de la passerelle

```sh
sudo lab/sim/gateway-firewall.sh                      # inclut UDP 1812/1813 sur wg-gw
docker build -t ecsi-cloud/radius:lab infra/radius
sudo LAB_STATE=lab/sim/.state lab/routeros/s3b/labo-s3b.sh services   # API (VOUCHER_CODE_KEY, RADIUS_VOUCHER_LOOKUP_KEY), worker (RADIUS_NAS_KEY)
sudo LAB_STATE=lab/sim/.state lab/routeros/s3b/labo-s3b.sh radius
```

`labo-s3b.sh radius` : Docker ne peut pas placer un conteneur dans un namespace `ip netns`. Le script exporte donc le système de fichiers de l'image (`docker create` + `docker export`) dans `$S3B/radius-rootfs`, y monte `/dev` et `/proc`, puis lance l'entrypoint de l'image avec `ip netns exec gw setsid chroot --userspec=10812:<gid>`. L'environnement (`RADIUS_LISTEN_ADDRESS=10.200.0.1`, `RADIUS_CLIENT_CIDR=10.200.0.0/24`, `RADIUS_DB_HOST=10.99.1.1`, `RADIUS_DB_PORT=15432`, mot de passe `ecsi_radius`, les deux clés lues dans le fichier d'environnement 0600) est exporté dans un sous-shell, jamais passé en argument. `labo-s3b.sh down` arrête ce processus et démonte. Sur un VPS, la passerelle WireGuard est dans le namespace de l'hôte : le service compose `radius` (`network_mode: host`) suffit.
