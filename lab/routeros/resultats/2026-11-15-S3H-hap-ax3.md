### Incident découvert : ancien pair WireGuard

La base ECSI CLOUD avait correctement attribué `10.200.0.2` au nouveau hAP, mais le noyau
WireGuard de la passerelle conservait encore un ancien pair historique utilisant
`10.200.0.2/32`.

L'agent gateway a correctement refusé d'écraser ce pair inconnu de la base.

Vérification de l'ancien pair avant retrait :

- aucune endpoint ;
- dernier handshake : 0 ;
- RX : 0 ;
- TX : 0 ;
- keepalive désactivé.

Seul cet ancien pair a été retiré de `wg0`. Les pairs actifs `.4` et `.5` n'ont pas été
modifiés.

Au cycle suivant, le gateway a installé automatiquement la clé publique du hAP sur
`10.200.0.2/32`.

Résultat :

- **PASS** handshake WireGuard réel entre le hAP physique et le VPS ;
- **PASS** trafic bidirectionnel ;
- **PASS** tunnel `10.200.0.2` opérationnel ;
- **PASS** aucun impact observé sur les routeurs `.4` et `.5`.

## Incident découvert : reprise d'enrôlement

L'échec du handshake s'est produit après la consommation réussie du jeton d'enrôlement.

État obtenu :

- routeur `PROVISIONING` ;
- `wg_public_key` déjà enregistrée ;
- jeton initial déjà consommé ;
- tunnel WireGuard ensuite fonctionnel ;
- étapes REST HTTPS et activation non exécutées.

L'interface ECSI CLOUD ne permet actuellement de renouveler l'enrôlement que si
`wgPublicKey` est absente. Le backend `renew()` refuse également un routeur qui possède déjà
sa clé publique et demande de le supprimer puis de le recréer.

Aucun mécanisme dédié de reprise après une interruption entre l'enrôlement et l'activation
n'a été trouvé.

Le protocole d'activation, lui, accepte correctement ce cas :
`router_activation_target()` sélectionne un routeur non supprimé, `PROVISIONING`, possédant
déjà une clé WireGuard.

Une reprise contrôlée des étapes 7–9 a donc été effectuée sans réutiliser le jeton initial,
sans changer l'adresse tunnel et sans remplacer la clé WireGuard.

## Défauts / dettes techniques découverts

### 1. Réconciliation d'un ancien pair WireGuard

Un tunnel IP redevenu attribuable en base peut rester occupé par un ancien pair dans l'état
WireGuard du noyau. Le gateway refuse alors correctement de remplacer automatiquement ce pair,
mais le nouvel enrôlement peut rester bloqué après consommation du jeton.

Une stratégie sûre de réconciliation/nettoyage des pairs historiques doit être définie.

### 2. Absence de reprise d'enrôlement après consommation du jeton

Si le jeton est consommé et que le script échoue avant l'activation, le routeur reste
`PROVISIONING` avec sa clé WireGuard enregistrée.

Dans cet état :

- le jeton ne doit pas être rejoué ;
- `renew()` refuse le renouvellement ;
- l'interface ne propose pas de renouvellement lorsque `wgPublicKey` existe ;
- supprimer/recréer le routeur n'est pas une récupération satisfaisante.

À prévoir : mécanisme explicite et sécurisé de **reprise d'activation** conservant la même
identité WireGuard et la même adresse tunnel, sans réutiliser le jeton d'enrôlement.
